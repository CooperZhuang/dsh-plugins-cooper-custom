# real：真实会话端到端评测

`../e2e` 用合成场景；这里用**真实会话**：从本地 DSH 的 session 日志里取样，让模型从真实对话里
出题，再用三种上下文作答，盲判。回答的问题是：**插件从那场真实会话里记住的东西，够不够回答
关于它的提问？**

## 三条臂

| 臂 | 模型看到什么 |
| --- | --- |
| `memory` | 只看到 `sourceSession` 关联到那场会话的记忆条目，用插件同款摘要 + 按需补注渲染 |
| `rag` | 那场会话的完整原文（上限 12k 字符；见「采样」） |
| `closed` | 什么都不给 |

判分用 `../e2e/judge.mjs` 的逐点判分器（必需点 `met` / 禁止点 `violated`，通过位由代码算），
判分时看不到臂名。跑之前先过 5 个锚点。

## 采样

`sample.mjs` 读 `<DSH_HOME>/sessions` 的持久会话日志（zstd，可解析 `session.v4.jsonl.zstd`），
只保留同时满足下列条件的会话：

- 用户/助手散文 10–160 条，总字符 800–24k，至少 2 条用户消息；
- 记忆库里至少有一条 `sourceSession` 指向它的条目（否则 `memory` 臂没有材料可看）；
- 转录先过 `redactSecrets`（GitHub/GitLab/sk-/AWS/JWT/私钥/`api_key=`/Bearer 等），
  再截到 12k 字符。

取样是**确定性的**：按日志 mtime 从新到旧取前 N 场。首轮统计：390 个日志、389 个可解析、
66 场满足条件、取 20 场；每场关联记忆 3–32 条。

## 出题与冻结

`author.mjs` 对每场会话出 2 个问题：答案必须在节选里被明确写下，优先耐久事实（决策、命令、
配置、约定、踩坑、偏好），每题给 `required`（1–3 条判分要点）、`forbidden`（0–1 条明确错误
说法）、`quote`（逐字节选）。`quote` 不是节选子串的问题直接丢弃。

出题后还会跑一遍 **verifier**（`author.mjs --verify`）：让模型只凭节选回答每个问题，答不了
或只能推断的题删掉——第一轮 38 题里删了 5 题（例如节选只写了现象、问题却问「为什么」）。

题库按会话/问题内容的 SHA-256 冻结在 `bench/data/real-bank.json`（gitignore）；重新出题是
新题库（`--force`），不与旧分数混算。

## 数据与隐私

- 所有中间产物都落在 `bench/data/`（已 gitignore）：`real-candidates.json`（含转录）、
  `real-bank.json`、`real-results.json`。**仓库里只有本文件的聚合数字**，没有转录、问题或回答。
- 发给 DeepSeek 的内容只有两样：`sample.mjs` 已做凭据擦除的转录，和由它生成的问题。
  本地默认对话路由本来就是 `deepseek-account`（同一会话内容已走 DeepSeek），这里不引入新的
  数据接收方；仍然建议只在谷时跑（00:30–08:30 半价）。
- 取样会话本身可能含个人信息；v1 只做了凭据擦除，没有做更细的脱敏。

## 运行

```bash
node bench/real/sample.mjs                       # 取样 → bench/data/real-candidates.json
node bench/real/author.mjs --provider deepseek   # 出题 → bench/data/real-bank.json（冻结）
node bench/real/author.mjs --provider deepseek --verify --force   # 出题后核一遍
node bench/real/run.mjs --provider deepseek      # 三臂作答 + 盲判
node bench/real/run.mjs --provider deepseek --limit 5             # 冒烟

# 抽取预算实验：重放抽取 → 只测 memory 臂
node bench/real/reextract.mjs --name more20 --max-memories 20 --max-output-tokens 8000 --provider deepseek
node bench/real/run.mjs --provider deepseek --reextract more20 --memory-only

# 联合召回：memory / raw / memory+raw / rag 四臂（需要本地 ollama 提供嵌入）
node bench/real/joint.mjs --provider deepseek
```

费用（首轮实测）：取样 0；出题 20 场约 ¥0.13；核题 38 题约 ¥0.22；作答+判分约见下。

## 结果（两轮，2026-11-05，谷时）

两轮的取样与转录相同，差别只在出题规则：

- **v1**：按「节选里有什么」出题，含易变值与「为什么」类问题；
- **v2**：出题加两条硬约束——只问耐久事实、不要问会随时间/部署变化的值（构建号、余额、行数、
  覆盖率等），核题器再加一个 `stable` 判定，不稳定就删。

| 轮 | 题库 | memory | rag | closed | 费用 |
| --- | --- | --- | --- | --- | --- |
| v1 | `b042f0a0…`，17 场 33 题 | 20/33（60.6%） | 31/33（93.9%） | 0/33 | ≈¥0.64 |
| **v2** | `acb35abc…`，19 场 33 题 | **22/33（66.7%）** | **32/33（97.0%）** | 0/33 | ≈¥0.71 |

v2 配对：memory 赢 RAG 0 题、输 10 题、平 23 题；memory 相对闭卷 22:0。
v2 费用：出题 ¥0.129 + 核题 ¥0.255 + 作答/判分 ¥0.302 + 诊断约 ¥0.02。

### 缺口诊断（`diagnose.mjs --llm`，离线看条目，不重新作答）

对每道 memory 失败的题，让模型先判「那场会话关联的记忆条目里有没有足够信息」，再判「一臂实际
展示的那块上下文（摘要 + 补注）里有没有」，于是失败被分成三类：

| 失败归因 | v1（13 题失败） | v2（11 题失败） |
| --- | --- | --- |
| 抽取缺口：条目里没有这条事实 | 10 | 6 |
| 展示缺口：条目有，但注入块没展示 | 0 | 0 |
| 回答缺口：注入块里有，回答漏了要点 | 3 | 5 |
| 窗口缺口：事实在最后 60 条消息之外 | 0 | 0 |

（60 条消息是插件 `extractWindowMessages` 的默认窗口；所有证据引文都落在窗口内，所以「长会话
早期被窗口跳过」在这一批里不是主因。）

### 抽取预算实验（同一批 v2 题目，只改每轮抽取上限）

`reextract.mjs` 用真实 `runExtraction`（同一 prompt、同一 quote 校验）把每场会话按抽取窗口重放
一遍，只改 `extractMaxMemories`；存储按变体隔离，再用 `run.mjs --reextract <name> --memory-only`
只测 memory 臂。这样 v2 题、判分器、上下文渲染都不变，唯一变量是每轮能留下多少条。

| 存储 | 每轮上限 | 条目数 | memory |
| --- | --- | --- | --- |
| live store（插件线上实际存的） | 5/次，多次 pass | ~170 | 22/33（66.7%） |
| replay base5 | 5 | 98 | 19/33（57.6%） |
| replay more10 | 10 | 175 | 22/33（66.7%） |
| **replay more20** | **20** | **236** | **24/33（72.7%）** |

三次 replay 的窗口、prompt、判分完全相同，是干净的剂量-反应曲线：**上限翻到 20，memory 从
19 涨到 24（+5 题）**；再往上受会话长度和抽取质量限制，涨幅在收窄。

对 more20 再跑一次归因：9 道失败 = **抽取缺口 4 ＋ 回答缺口 5**（展示缺口、窗口缺口仍是 0）。
也就是说预算能把抽取缺口从 6 压到 4，但**回答侧那 5 道一点没动**，它已经成了更大的那一半。

（live 与 replay 不能直接比：线上是会话边跑边多次抽取，replay 是事后按窗口重放；只有三个
replay 变体之间是同一条件。另外 replay 的条目更多会挤占 4KB 注入预算，所以「存得更多」不一定
线性变成「答得更对」。）

实验费用：三次重放 ¥0.249 + ¥0.605 + ¥0.688，三次 memory 打分约 ¥0.49，归因约 ¥0.03。

### 说明什么

1. **v2 把出题收窄到耐久事实后，memory 只从 60.6% 升到 66.7%，RAG 从 93.9% 升到 97.0%——
   差距没有缩小，反而还是约 10 题。** 易变值问题不是 memory 落后的主因。
2. **展示缺口为 0**：条目里有的东西，摘要/补注确实送到上下文了。真实会话上的瓶颈不在召回。
3. **抽取预算是一个真实杠杆，但不够**：同一个 replay 条件下，每轮上限 5→10→20，memory
   19→22→24 题；到 20 时抽取缺口降到 4，但离 RAG 的 32 还差 8 题。把默认上限从 5 提到 20
   会换来约 +2 题（相对线上 22/33）和 2.4 倍的条目量，值不值得要按注入/合并成本另算。
4. **回答侧也可控**：more20 的 9 道失败里 5 道是「注入块里有、回答没覆盖」；把答案 prompt
   改成「有就直说、每个数字/名称都写出来」后，同条件下 24→26 题，回答缺口降到 4。剩下还有
   题目本身的缺陷（要求原文没有的推断）。
5. 真实会话上 memory 即使加预算（24/33）仍明显不如把整段原文塞进去（32/33）；合成题库的
   「memory≈RAG」不能外推到真实会话。

### 复查命令

```bash
node bench/real/diagnose.mjs                    # 无模型的窗口/ token 口径
node bench/real/diagnose.mjs --llm --provider deepseek   # 三类归因（约 ¥0.02）
```
### 回答侧变体（more20 store，同一批题、同一判分）

more20 的失败里 5 道是「注入块里有、回答没覆盖」，所以再试一次答案侧：`--answer-variant commit`
把「资料里有就直接给结论、问题问到的每个数字/名称/日期都写出来，别用『资料没有提到』回避」
写进答案 prompt。其它一切不变。

| answer prompt | memory | 失败归因 |
| --- | --- | --- |
| complete（默认） | 24/33（72.7%） | 抽取 4 ＋ 回答 5 |
| **commit** | **26/33（78.8%）** | 抽取 3 ＋ 回答 4 |

答案侧的克制确实值 +2 题；加上抽取预算，memory 从线上 22/33 提到 26/33（78.8%），离 RAG 的
32/33 还差 6 题。剩下的 7 道失败里仍有 3 道是条目里就没有那条事实，另外 4 道里至少一道是题目
本身要求了原文没有的点（`f5de8814-2`）——**存储和回答两侧都还有空间，但都不是「召回没召到」**。

## 联合召回实验（记忆 + 原始会话片段）

前几轮已经证明：memory 失败里展示缺口为 0，瓶颈是抽取丢细节与回答覆盖。于是按 Memory-Tax 的
结论做一次对照——**把「记忆」和「同一会话的原始片段」一起给模型**，看能不能补回差距。

做法（[joint.mjs](./joint.mjs)）：
每场会话的转录按消息边界切 ~900 字符的块；问题到来时用 **字符 bigram BM25 + 本地
qwen3-embedding 余弦 + RRF(k=60)** 在**该会话自己的块**里取 top-3，拼进上下文（原文预算
2.2KB）。memory 臂用 more20 重放 store + commit 答案 prompt。四条臂同题、同判分器：

| 臂 | 通过 | 上下文量级 |
| --- | --- | --- |
| memory | 26/33（78.8%） | ~4KB 记忆摘要+补注 |
| raw（top-3 检索片段） | 27/33（81.8%） | ~2.2KB |
| memory+raw（dense 混合检索） | **32/33（97.0%）** | ~6KB |
| memory+raw（本地生产路径：引文定位 + 词面回退） | 30/33（90.9%） | ~6KB |
| memory+raw（纯词面窗口） | 28–31/33（三次） | ~6KB |
| rag（整段原文 ≤12k） | 33/33（100%） | 12k |

配对：memory+raw 对 memory **赢 6 / 输 0**；对 rag **赢 0 / 输 1**。费用 269 次调用 ≈ **¥0.93**。

两点值得记住：

1. **单靠 raw 不够**（27/33）：top-3 片段检索会漏掉没进块或排名靠后的细节；单靠 memory 也不够
   （26/33）：抽取时丢的细节补不回来。两者拼起来才到 32/33——和 Memory-Tax 的「联合检索原文」
   结论一致。
2. 这个组合只用 ~6KB 上下文就达到整段 12KB 的 97%，说明**插件该抄的不是更花哨的记忆结构，而是
   在召回时把原始会话片段当成第二路候选**（companion-memory 的 turn_recall 是同一件事）。
3. 生产版没有 embedding：它先用记忆条目里存的逐字 `quote` 在来源会话里做字符串定位（33/33 的题
   至少有一条被召回记忆的 quote 能在原文里找到），找不到再退回词面窗口。实测 30/33，比纯词面
   好、比 dense 混合差 2 题；这个差距是「要不要给插件引入本地 embedding」的取舍依据。

## 限定

- 两轮都是**小样本**：17/19 场会话、每轮 33 道题、每条臂单次采样；不能外推到所有会话。
- 抽取预算实验是**回放**：每场会话按日志重放一次抽取，和线上边跑边抽的时点不同；三个 replay
  变体之间可比，但不能把某次 replay 分数当成线上分数。
- 两轮的题不同（不同题库），所以 v1→v2 的分数差**不能**读成「评测变好了」，只能说「在更公平的
  出题规则下，memory 的劣势依然存在」。
- v2 出题/核题仍不完美：还有题在问精确到秒的时间；核题器有 2 题因回复不是 JSON 被误删。
- 缺口归因也是模型判的（`diagnose.mjs --llm`），不是人工逐题确认；三类边界（尤其「回答漏要点」
  和「判分过严」）很难机械区分。
- 真实会话的题是模型按「节选里有什么」出的，不是按「插件该记什么」出的；已有 2 题问到会话里
  明确说不要记的易变值，这类题对 memory 臂天然不公。
- 取样要求「那场会话至少产出了一条记忆」，所以它衡量的是「已经记过东西的会话里，记得够不够」，
  不衡量「从零开始该不该记」。
- 题目由模型写、核题也由模型判：题目可能偏简单或偏冷门，verifier 可能误删或漏删。
- 判分与生成同家族模型（deepseek-chat），没有多票和人工逐题复核；答案仍可能是「部分正确」被
  判负或「蒙对」被判正。
- RAG 臂给的是截到 12k 字符的节选，不是会话全量；它代表「把这段原文全塞进去」的上限，不是
  无限上下文。
