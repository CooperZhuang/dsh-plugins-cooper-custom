# e2e：端到端记忆评测

回答一个问题：**这条记忆到底帮没帮上忙**。`../run-bench.mjs` 只测「目标条目有没有排进前 N」，
`run-bench` 的 R@1 高不等于答得对；这里测的是答案。

## 三条臂

同一批冻结题目，三条臂分别答题：

| 臂 | 模型看到什么 | 它代表什么 |
| --- | --- | --- |
| `memory` | 真实抽取流程挖出的记忆，加上插件同款的摘要 + 按需补注上下文 | 我们实际交付的东西 |
| `rag` | 该场景的整段对话原文 | 笨办法的上限（全历史 RAG） |
| `closed` | 什么都不给 | 闭卷对照：能猜对的题不算记忆的功劳 |

判分是**盲评**：判分模型只看到问题、必需点、禁止点和回答，看不到回答来自哪条臂，所以通过率
不可能靠臂名影响。`required` / `forbidden` 按语义判，不要求原词。

## 题库

题库分两个文件：`scenarios.mjs`（首轮 23 条，保持字节不变，已有结果可追溯）和
`scenarios-extra.mjs`（P1 扩充 30 条，10 个类别各 3 条），合计 53 条。题目是中文，事实都写在
对话里，不依赖外部知识。题库是**合成**的，不含真实会话与隐私，所以可以入库；真实记忆库只用于
`../` 下的检索基准。`run.mjs` 把两批拼成一个 bank 再取哈希，所以扩题不会改掉旧题的哈希含义。

写题规则（抄自 companion-memory 的作者规则）：

- 一个场景一个事实组，项目/产品名不跨场景复用，否则后一个场景会悄悄改掉前一个答案；
- 事实必须在对话里明说，不能靠推断；
- 问题不能描述它提问时点之后才发生的事；
- 相对时间必须在题面里说清指哪一天。

## 运行

```bash
# 本地 ollama（免费、离线、可复现）
node bench/e2e/run.mjs

# 在线 DeepSeek（谷时 00:30–08:30 半价；53 个场景全量抽取约 ¥0.27，只重跑答案约 ¥0.13）
node bench/e2e/run.mjs --provider deepseek

# 冒烟 / 只跑指定场景
node bench/e2e/run.mjs --limit 3
node bench/e2e/run.mjs --provider deepseek --only hot-reload-restart,open-plan-tomorrow

# 复用上一轮的抽取，只改答案 prompt 或判分器时用（把变量隔离出来）
node bench/e2e/run.mjs --provider deepseek --reuse-store

# 只重判已存答案（不调用生成）：换判分规则后改分数，原文件不动
node bench/e2e/run.mjs --provider deepseek --regrade bench/data/e2e-results.json
```

DeepSeek 的 key 从环境变量 `DEEPSEEK_API_KEY` 或 `~/.dsh/.credentials.yaml` 的
`DEEPSEEK_API_KEY` 读取，不会打印。也可以用 `--key-file` 指别的文件。
`--model` 可以换模型；报告里记录 provider/model/谷时与否/实际 token 与估算费用。

## 冻结与读数守则

- 每次运行会把 `scenarios` 的 SHA-256 写进结果；**改了题库，旧结果作废**，不要拿旧分数配新题。
  当前是 bank v2（`23876acceb0e…`）；bank v1（`9cece6602e01…`）的结果只留档，不混算。
- 结果落在 `bench/data/e2e-results.{json,md}`（已 gitignore）。逐题回答和判分理由都在 JSON 里，
  失败时先看原始回答，不要只看汇总。
- 数字只用来看方向：判分与生成同家族模型、场景数 53、每条臂只有一次采样。所以报告同时给
  闭卷对照和配对输赢，避免把「能猜对」算成「记得住」。
- 抽取是否遵守证据契约也在这里上报：`rejected by the quote check` 是被 P0-A 的引文校验挡下的
  候选数；它高不是坏事，说明检查在工作，但持续高要去看抽取模型是否在改写引文。
- 没有随机种子/多票/人工复核：这是第一版基线，不是论文级评测。要下强结论前先扩题库、
  加多票，并按 companion-memory 的做法把题库/答案/判据在跑之前冻住。

## 判分器 v5 与 P1/P2 修复

每轮暴露的问题都修掉并留痕：

- **禁止点语义（v2 → v4）**：禁止点只有在回答把它当作正确/当前事实支持时才算违反；回答把它当
  例外、条件、对照提起，明确否定它，或说它不成立，都不算。实测里判分器连续把「不要相信双击
  结果」「禁止直接在 main 上改」判成违反——所以规则从「否定/相反说法」再收紧到「只看主张、
  不看词语重合」，并加了对应锚点。
- **逐点判分（v5）**：一条回答里同时有「答对的部分」和「提到禁止点的词」时，整体 pass/fail
  仍会串味。v5 改成逐条返回 `required[].met` / `forbidden[].violated`，通过位由代码算，
  不再信任模型给的整体结论。第五轮重判时它把 `snapshot-latency` 的误判改回，也把
  `branch-strategy` 一处「只说了分支、没说是从 main 切出」的漏项判了出来——一正一反，聚合不变。
- 开跑前跑 6 个锚点（应通过/应失败/相反说法/部分回答/否定禁止点/逐点格式），不过会在日志
  告警并写进报告。
- **未完成 loops 进注入**：memory 臂现在和插件一样，把 open loops 拼进同一块注入上下文；
  插件侧也改了（`renderOpenLoops`，带 4 条/600B 上限，库为空只有 loop 时也注入）。
- **相对时间**：抽取调用的 prompt 现在带上「今天是 YYYY-MM-DD（用户本地日期）」，并要求 loop
  文本保留「明天/周五」这类原话、`dueAt` 按今天换算；超出 ±窗口的离谱日期会被丢弃
  （首轮模型把「明天」解析成了四个月前的日期，渲染成 overdue，直接毁掉这条 loop）。
- **loop 解析容错**：模型返回裸字符串数组（`["把截图补齐", …]`）时按 text 接受——首轮就是
  这个形状，被解析器整段丢掉，才让 memory 臂答「不知道」。

### 五轮里修掉的东西

| 轮次暴露 | 归类 | 修法 |
| --- | --- | --- |
| `sinatra-port` memory 判负 | 判分器误判（例外被当违反） | 判分器 v2：禁止点只有被肯定才算；加锚点自检 |
| `open-plan-tomorrow` memory 答不知道 | 产品缺口（loops 不进上下文） | 注入块加 open loops；库为空只有 loop 也注入 |
| loop 全被丢 | 解析容错（模型返回裸字符串数组） | `parseLoops` 接受裸字符串 |
| loop 文本丢「明天」、dueAt 解析成四个月前 | 抽取缺当前日期 | prompt 带「今天是 YYYY-MM-DD」；保留时间原话；离谱 dueAt 丢弃 |
| 第 2 轮 `plan-*` 仍看不到 loop | 注入上限（4 条、按 oldest 排） | 上限 8 条/800B，无日期按最新在前 |
| 第 2 轮 `commit-msg-ticket` 被判「不知道本项目」 | harness 缺陷（53 个场景共用一个 project 作用域） | 按场景隔离 store |
| `snapshot-latency` memory 判负 | 判分器误判（回答说的是禁止点的反面） | 判分器 v3：相反说法不算违反；加锚点 |
| 第 3 轮 `open-plan` 两臂都漏第二个承诺 | 答案 prompt 只要求「一两句话」 | 第四轮改成「问题问到的每件事都要答到」 |
| 第 4 轮 `windows-path-quirk`/`branch-strategy` memory 判负 | 判分器把「否定禁止点」当肯定（「不要相信双击结果」） | 判分器 v4：只看主张、不看词语重合；加否定锚点 |
| `rabbitmq-vhost-queue` 反复判负 | 题库缺陷（两个主体被并成一个「这个服务」） | bank v2：题面按主体拆开；旧题库结果留档不混算 |
| 第 5 轮 `snapshot-latency` rag 被判负 | 整体判分仍会把「旧配置」读成禁止点 | 判分器 v5：必需点/禁止点逐条判，通过位由代码算；加逐点锚点 |

### 第五轮逐题复核

- memory 臂 **53/53**，没有失败；rag 臂唯一失败是 `branch-strategy`：「在 feature 分支上改，
  合并前先 rebase 一遍」——没说「从 main 切出」，v5 逐点判分把它判负，属于**答案漏项**，保留。
- `rabbitmq-vhost-queue` 在 bank v2 下 memory 与 rag 都通过，证实第四轮那个失败确实是题面把两个
  主体并成一个服务的缺陷，不是记忆问题。
- v5 逐点重判与 v4 整体判分的聚合一致（53/53 与 52/53），但有两处单题判决相反：
  `snapshot-latency` rag 的误判被改回通过；`branch-strategy` rag 被更严格的必需点判定判负。
- 没有需要人工改判的行了。

### 这些数字能说明什么

- 闭卷 0/53：题库确实是记忆依赖的，不是常识能猜的。
- 当前口径（bank v2 + 判分器 v5）：memory 53/53、rag 52/53、closed 0/53。**memory 不输给
  「把整段原文塞进去」**，而且上下文约 4KB，rag 是整段对话。
- 和 companion-memory「六轮优化仍没赢 RAG」对照：它的 RAG 是上限参照且用了同样的原文；
  我们这里 memory 略高 1 题，但样本只有 53、单次采样，**不能当成普遍优势**，只能说「没有明显
  落后」。
- **不能说明**：真实长期会话上的效果、53 题之外的泛化、判分器残余误判（前后至少 5 处单题
  误判，全靠逐点判分和人工复核兜住）。判分与生成同家族模型、单次采样、无多票。
