# e2e：端到端记忆评测

回答一个问题：**这条记忆到底帮没帮上忙**。`../run-bench.mjs` 只测「目标条目有没有排进前 N」，
`run-bench` 的 R@1 高不等于答得对；这里测的是答案。

## 三条臂

同一批冻结题目，三条臂分别答题：

| 臂 | 模型看到什么 | 它代表什么 |
| --- | --- | --- |
| `memory` | 真实抽取流程挖出的记忆，加上插件同款的摘要 + 按需补注上下文 | 我们实际交付的东西 |
| `rag` | 该场景的整段对话原文 | 笨办法的上限（全历史 RAG） |
| `closed` | 什么都不给 | 闭卷对照：能猜对的题不算记忆的功劳 |

判分是**盲评**：判分模型只看到问题、必需点、禁止点和回答，看不到回答来自哪条臂，所以通过率
不可能靠臂名影响。`required` / `forbidden` 按语义判，不要求原词。

## 题库

题库分两个文件：`scenarios.mjs`（首轮 23 条，保持字节不变，已有结果可追溯）和
`scenarios-extra.mjs`（P1 扩充 30 条，10 个类别各 3 条），合计 53 条。题目是中文，事实都写在
对话里，不依赖外部知识。题库是**合成**的，不含真实会话与隐私，所以可以入库；真实记忆库只用于
`../` 下的检索基准。`run.mjs` 把两批拼成一个 bank 再取哈希，所以扩题不会改掉旧题的哈希含义。

写题规则（抄自 companion-memory 的作者规则）：

- 一个场景一个事实组，项目/产品名不跨场景复用，否则后一个场景会悄悄改掉前一个答案；
- 事实必须在对话里明说，不能靠推断；
- 问题不能描述它提问时点之后才发生的事；
- 相对时间必须在题面里说清指哪一天。

## 运行

```bash
# 本地 ollama（免费、离线、可复现）
node bench/e2e/run.mjs

# 在线 DeepSeek（谷时 00:30–08:30 半价；23 个场景全套约 ¥0.1）
node bench/e2e/run.mjs --provider deepseek

# 冒烟
node bench/e2e/run.mjs --limit 3
```

DeepSeek 的 key 从环境变量 `DEEPSEEK_API_KEY` 或 `~/.dsh/.credentials.yaml` 的
`DEEPSEEK_API_KEY` 读取，不会打印。也可以用 `--key-file` 指别的文件。
`--model` 可以换模型；报告里记录 provider/model/谷时与否/实际 token 与估算费用。

## 冻结与读数守则

- 每次运行会把 `scenarios` 的 SHA-256 写进结果；**改了题库，旧结果作废**，不要拿旧分数配新题。
- 结果落在 `bench/data/e2e-results.{json,md}`（已 gitignore）。逐题回答和判分理由都在 JSON 里，
  失败时先看原始回答，不要只看汇总。
- 数字只用来看方向：本地小模型判分、场景数 23、每条臂只有一次采样。所以报告同时给闭卷对照
  和配对输赢，避免把「能猜对」算成「记得住」。
- 抽取是否遵守证据契约也在这里上报：`rejected by the quote check` 是被 P0-A 的引文校验挡下的
  候选数；它高不是坏事，说明检查在工作，但持续高要去看抽取模型是否在改写引文。
- 没有随机种子/多票/人工复核：这是第一版基线，不是论文级评测。要下强结论前先扩题库、
  加多票，并按 companion-memory 的做法把题库/答案/判据在跑之前冻住。

## 判分器 v2 与 P1 修复

首轮暴露的问题在这一轮修掉了，逐条留痕：

- **禁止点语义**：判分器现在明确「禁止点只有在回答把它当作问题答案/当前事实肯定时才算违反」，
  回答把它当例外/条件/对照提起不算。开跑前先跑一对固定锚点（一个该通过的正确回答、一个该失败
  的错误回答），锚点不过会在日志里告警并写进报告，避免判分器本身坏掉却继续打分。
- **未完成 loops 进注入**：memory 臂现在和插件一样，把 open loops 拼进同一块注入上下文；
  插件侧也改了（`renderOpenLoops`，带 4 条/600B 上限，库为空只有 loop 时也注入）。
- **相对时间**：抽取调用的 prompt 现在带上「今天是 YYYY-MM-DD（用户本地日期）」，并要求 loop
  文本保留「明天/周五」这类原话、`dueAt` 按今天换算；超出 ±窗口的离谱日期会被丢弃
  （首轮模型把「明天」解析成了四个月前的日期，渲染成 overdue，直接毁掉这条 loop）。
- **loop 解析容错**：模型返回裸字符串数组（`["把截图补齐", …]`）时按 text 接受——首轮就是
  这个形状，被解析器整段丢掉，才让 memory 臂答「不知道」。

## 结果（三轮 + 判分器复核，2026-11-05 谷时）

全部用 `deepseek-chat`、谷时半价，题库与判分规则每轮都在跑之前定下；失败不删分母。

| 轮 | 题库 | 口径 | memory | rag | closed | 费用 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 23 | 首轮 | 21/23（91.3%） | 22/23（95.7%） | 0/23 | ¥0.117 |
| 2 | 53 | 单库池化 | 50/53（94.3%） | 51/53（96.2%） | 0/53 | ¥0.319 |
| 3 | 53 | 按场景隔离 | 50/53（94.3%） | 52/53（98.1%） | 0/53 | ¥0.269 |
| 3′ | 53 | 判分器 v3 重判答案 | **51/53（96.2%）** | 52/53（98.1%） | 0/53 | 约 ¥0.10 |

第三轮是当前口径：每个场景一个独立 store（真实工作区各自有项目作用域），loop 跟着该
场景走；判分器 v3 只重判已存答案，不重新生成（`--regrade`，原分数保留在
`e2e-results.json`，重判在 `e2e-results-regraded.json`）。

### 三轮里修掉的东西

| 轮次暴露 | 归类 | 修法 |
| --- | --- | --- |
| `sinatra-port` memory 判负 | 判分器误判（例外被当违反） | 判分器 v2：禁止点只有被肯定才算；加锚点自检 |
| `open-plan-tomorrow` memory 答不知道 | 产品缺口（loops 不进上下文） | 注入块加 open loops；库为空只有 loop 也注入 |
| loop 全被丢 | 解析容错（模型返回裸字符串数组） | `parseLoops` 接受裸字符串 |
| loop 文本丢「明天」、dueAt 解析成四个月前的日期 | 抽取缺当前日期 | prompt 带「今天是 YYYY-MM-DD」；保留时间原话；离谱 dueAt 丢弃 |
| 第 2 轮 `plan-*` 仍看不到 loop | 注入上限（4 条、按 oldest 排） | 上限 8 条/800B，未定日期的按最新在前 |
| 第 2 轮 `commit-msg-ticket` 被判「不知道本项目」 | harness 缺陷（53 个场景共用一个 project 作用域） | 第三轮改成按场景隔离 store |
| `snapshot-latency` memory 判负 | 判分器误判（回答说的是禁止点的反面） | 判分器 v3：明确否定/相反说法不算违反；加第二个锚点 |

### 第三轮逐题复核（原始 50/53 之外）

- `snapshot-latency` / memory：回答「2026-09-30 压测时 31ms/142ms，但这是旧限流配置下的读数」。
  禁止点是「这些数字是改限流后的配置测出来的」——回答说的正好相反，判分器却判成表达禁止点。
  **判分器误判**，v3 重判已改回通过（就是 51/53 里的 +1）。
- `rabbitmq-vhost-queue` / memory：题面问「这个服务连的 RabbitMQ vhost 和主消费队列分别叫什么」，
  但对话里 `order.batch.v3` 属于「对账单」，不是「蓝莓队列」。memory 臂答「vhost 是 /bq-prod，
  该服务的主消费队列资料没给」——按题面这是**更正确**的回答。这是**题库缺陷**（两个主体被并成
  一个服务），不是记忆缺陷。做有效性修正时把这题从双方分母都去掉：52 题上 memory 51/52、
  rag 51/52，**两者打平**。
- `open-plan-tomorrow` / memory 与 rag：都只答了「补登录页截图」，漏了「发之前先自己过文案」。
  上下文里两条 loop / 整段原文都在，是**答案生成漏项**，两边都失败，保留在分母里。

### 这些数字能说明什么

- 闭卷 0/53：23 与 53 两轮都是零，说明这些题确实依赖记忆，不是靠常识猜的。
- 在当前 53 题上，memory 与 rag 打平（有效性修正后都是 51/52）；memory 相对闭卷 51:0。
- 和 companion-memory「六轮优化仍没赢 RAG」一致：结构化记忆没有超过“把原文全塞进去”，
  只是用更小的上下文（约 4KB vs 整段对话）达到同样水平。
- **不能说明**：真实长期会话上的效果、判分器没有残余误判（只做了锚点 + 人工复核两处）、
  53 题之外的泛化。判分模型与生成模型同家族、单次采样、无多票。
