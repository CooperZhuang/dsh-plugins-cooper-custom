# e2e：端到端记忆评测

回答一个问题：**这条记忆到底帮没帮上忙**。`../run-bench.mjs` 只测「目标条目有没有排进前 N」，
`run-bench` 的 R@1 高不等于答得对；这里测的是答案。

## 三条臂

同一批冻结题目，三条臂分别答题：

| 臂 | 模型看到什么 | 它代表什么 |
| --- | --- | --- |
| `memory` | 真实抽取流程挖出的记忆，加上插件同款的摘要 + 按需补注上下文 | 我们实际交付的东西 |
| `rag` | 该场景的整段对话原文 | 笨办法的上限（全历史 RAG） |
| `closed` | 什么都不给 | 闭卷对照：能猜对的题不算记忆的功劳 |

判分是**盲评**：判分模型只看到问题、必需点、禁止点和回答，看不到回答来自哪条臂，所以通过率
不可能靠臂名影响。`required` / `forbidden` 按语义判，不要求原词。

## 题库

`scenarios.mjs` 里有 23 个合成场景，覆盖命令/约定、架构决策、踩坑、偏好边界、更正、计划、
时间快照、第三方文档等类别。题目是中文，事实都写在对话里，不依赖外部知识。题库是**合成**的，
不含真实会话与隐私，所以可以入库；真实记忆库只用于 `../` 下的检索基准。

写题规则（抄自 companion-memory 的作者规则）：

- 一个场景一个事实组，项目/产品名不跨场景复用，否则后一个场景会悄悄改掉前一个答案；
- 事实必须在对话里明说，不能靠推断；
- 问题不能描述它提问时点之后才发生的事；
- 相对时间必须在题面里说清指哪一天。

## 运行

```bash
# 本地 ollama（免费、离线、可复现）
node bench/e2e/run.mjs

# 在线 DeepSeek（谷时 00:30–08:30 半价；23 个场景全套约 ¥0.1）
node bench/e2e/run.mjs --provider deepseek

# 冒烟
node bench/e2e/run.mjs --limit 3
```

DeepSeek 的 key 从环境变量 `DEEPSEEK_API_KEY` 或 `~/.dsh/.credentials.yaml` 的
`DEEPSEEK_API_KEY` 读取，不会打印。也可以用 `--key-file` 指别的文件。
`--model` 可以换模型；报告里记录 provider/model/谷时与否/实际 token 与估算费用。

## 冻结与读数守则

- 每次运行会把 `scenarios` 的 SHA-256 写进结果；**改了题库，旧结果作废**，不要拿旧分数配新题。
- 结果落在 `bench/data/e2e-results.{json,md}`（已 gitignore）。逐题回答和判分理由都在 JSON 里，
  失败时先看原始回答，不要只看汇总。
- 数字只用来看方向：本地小模型判分、场景数 23、每条臂只有一次采样。所以报告同时给闭卷对照
  和配对输赢，避免把「能猜对」算成「记得住」。
- 抽取是否遵守证据契约也在这里上报：`rejected by the quote check` 是被 P0-A 的引文校验挡下的
  候选数；它高不是坏事，说明检查在工作，但持续高要去看抽取模型是否在改写引文。
- 没有随机种子/多票/人工复核：这是第一版基线，不是论文级评测。要下强结论前先扩题库、
  加多票，并按 companion-memory 的做法把题库/答案/判据在跑之前冻住。

## 首轮结果（2026-11-05，谷时）

`deepseek-chat`，23 个场景，题库哈希 `73e42fbe…`，161 次调用 / 81,184 in + 8,854 out tokens，
估算 ¥0.117（谷时半价）。逐题原始回答在 `bench/data/e2e-results.json`。

| 臂 | 原始判分 | 复核后 |
| --- | --- | --- |
| memory（抽取+注入+补注） | 91.3%（21/23） | 95.7%（22/23） |
| rag（整段对话原文） | 95.7%（22/23） | 95.7%（22/23） |
| closed（无资料） | 0%（0/23） | 0%（0/23） |

抽取侧：36 个候选全部入库，引文校验拒绝 0 个——DeepSeek 确实按 P0-A 的契约逐字引用，
条目里 `quote` / `evidenceSeq` 都落了盘。1 个场景一条没存（见下）。

**两处失败逐个复核：**

1. `sinatra-port` / memory：回答是「本地固定 4567，3000 会跟其他项目冲突；**CI 环境仍可用 3000**」，
   判分器把「CI 里可用 3000」当成禁止点「本地用 3000」判负。这是**判分器的误判**：禁止点的
   条件是「本地用 3000」，回答明确说的是 CI 例外。复核改判为通过；题库未改（改题会让整轮数字
   失去可比性），下次跑之前应把禁止点写成「本地开发必须用 3000」。
2. `open-plan-tomorrow` / memory：回答「不知道」，因为抽取阶段 0 条入库。模型把「明天补截图、
   发之前先过文案」当成**开放事项**（`loops`）而不是持久记忆，而插件当前只注入 memories，
   loops 不进上下文。这是真实产品缺口，不是判分问题；RAG 臂也只答了「补截图」漏了「先过文案」，
   判负合理。下一步值得评估「把未完成 loops 也放进入口上下文」，但那是 P1，不是这轮评测的结论。

**这些数字能说明什么：** 在这 23 个合成场景里，记忆臂显著高于闭卷（21:0），说明记忆确实在提供
信息；但它仍略低于整段原文（0 赢 1 输），和 companion-memory「改了六轮仍没赢 RAG」的结论一致。
**不能说明**：真实长期会话上的效果、23 题之外的泛化、多票判分下的稳定性。样本量小，只当方向。
